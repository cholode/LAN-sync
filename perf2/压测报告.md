# LAN-IM 第二轮压测报告（perf2）

## 1. 测试概述

- 测试时间：2026-08-16
- 目标地址：`http://8.130.151.211`
- WebSocket 地址：`ws://8.130.151.211/api/v1/ws`
- 监控端点：`http://8.130.151.211:6060/metrics`
- 压测数据目录：`perf2/`
- 原始指标采样：`perf2/metrics/`
- 压测工具：k6 v1.6.1、Node.js 指标采集器
- 本次不压测 Agent
- 本次不做长连接长时间保持
- 不在启用 Agent 的群聊中压测
- 登录采用 bcrypt，属于固定成本场景，因此登录压测单独慢爬坡

## 2. 总体结论

- 普通 HTTP 读接口在 20 VU 内可用，50 VU 开始出现成员列表查询失败，建议将并发上限控制在 20 VU 以下。
- 登录吞吐约 8 QPS，主要受 bcrypt 运算限制；并发增加时延迟线性上升。
- WebSocket 短连接 500 并发建连全部成功，建连 P95 约 130ms。
- 9 人房间短消息广播在目标 500 msg/s 时端到端 P95 约 45ms，服务端 Kafka 消费滞后为 0。
- 群聊广播在 100 人规模表现稳定；500 人时 Hub 任务池达到容量上限 256，端到端延迟出现长尾。
- 1000 人规模时服务端峰值在线 912，K6 累计发起 1040 个会话，服务端成功建连约 913 个，约 87.8%；属于容量边界，不推荐生产长期运行在 1000 人单群全在线广播场景。

## 3. 测试方法

- `users.json`：2000 个测试用户。
- `rooms.json`：10/100/500/1000 人房间映射为 `2/3/4/5`。
- 指标采集：每 2 秒抓取一次 Prometheus 文本指标，保存到 `perf2/metrics/`。
- 指标摘要：`perf2/metrics_summary.json`、`perf2/report_table.tsv`。

## 4. HTTP 只读接口

| ----- | ------ | ----- | ------ | ------ | ------------------------ |
| 5 VU  | 100%   | 26.56 | 575ms  | 800ms  | 稳定                       |
| 10 VU | 100%   | 32.27 | 1.48s  | 1.72s  | 可用                       |
| 20 VU | 100%   | 34.0  | 3.48s  | 4.11s  | 延迟明显上升                   |
| 50 VU | 98.91% | -     | 14.93s | 19.96s | `members` 接口 6/106 失败，停止 |

服务端采样显示，50 VU 时 MySQL 使用中连接峰值 50，数据库查询平均耗时从 0.49ms 升至 8.84ms。接口延迟主要来自数据库查询放大，而非单纯网络问题。

| 场景           | WS 峰值在线 | Hub 运行任务峰值 | Kafka 消费滞后峰值 | MySQL 使用连接峰值 | Redis 平均延迟 |
| ------------ | ------- | ---------- | ------------ | ------------ | ---------- |
| 基线           | 0       | 0          | 0            | 0            | -          |
| HTTP 50 VU   | 0       | 0          | 0            | 50           | 2.32ms     |
| WS 500 短连接   | 500     | 0          | 0            | 0            | 26.73ms    |
| 消息 500 msg/s | 9       | 1          | 0            | 0            | 0.09ms     |
| 广播 100       | 100     | 1          | 0            | 0            | 0.26ms     |

说明：

- `Hub 运行任务峰值 256` 与线程池容量一致，500/1000 广播时已达到上限。
- `im_hub_task_pool_waiting` 全程为 0，但运行任务已打满，后续需关注任务排队策略。
- Kafka 消费滞后全程为 0，消息生产与消费链路未见堆积。
- 1000 人广播时 MySQL 打开连接池从 52 扩展到 193，建议生产环境设置合理连接池上限并观察连接回收。

## 10. 主要风险

- bcrypt 登录吞吐固定约 8 QPS，容易被慢速登录请求拖住 CPU。
- HTTP 读接口在 20 VU 后延迟快速上升，50 VU 已出现 `members` 失败。
- 500 人以上群广播时 Hub 任务池已打满，端到端延迟出现明显长尾。
- 1000 人全在线广播达到当前单节点容量边界，建连成功率下降到约 87.8%。

## 11. 优化建议

- 登录接口增加独立服务或引入异步登录/验证码限流，隔离 bcrypt 计算。
- `members` 和历史消息接口增加缓存，减少数据库直查压力。
- 将 Hub 任务池容量与可观测性关联，增加拒绝/等待计数，必要时调整容量或拆分房间。
- 对 1000 人群广播场景做连接速率限制、消息合并或分组推送，降低瞬时扇出。
- 集群化时优先拆分 Hub 和 Kafka consumer，避免单节点广播瓶颈。
- 保留本轮 `perf2/metrics` 原始采样，便于后续用 Grafana/Prometheus 回放分析。
