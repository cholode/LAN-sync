# WebSocket 分片压测分析（perf4）

## 1. 核心结论

- Hub 按用户/房间分片是有效的，主要收益体现在 500/1000 人群广播的端到端延迟下降。
- 500 人广播 E2E P95 从上轮 243.3ms 降至 99ms，降幅约 59%。
- 1000 人广播 E2E P95 从上轮 180ms 降至 71ms，降幅约 61%。
- 1000 并发纯建连服务端峰值在线 938/1000，比上轮 912 提升约 2.9%。
- 结合云监控：CPU 在压测期间达到 100%，这是当前 1000 并发建连长尾的首要嫌疑，而不是 fd/accept 或 DB/Redis。

## 2. 分片效果判断

### 2.1 建连路径

100/500 VU 建连成功率 100%，P95 建连耗时稳定在 88ms 左右，说明分片后的 `Register`/`Unregister` 在 500 并发内没有成为瓶颈。

1000 VU 时：

- P50 仍约 80.64ms，P90 约 90.72ms，说明绝大多数连接仍然很快。
- P95 拉长到 1.04s，最大 21.06s，说明存在明显长尾。
- 服务端峰值在线 938，而不是 1000，尾部连接进入超时重试。
- 云监控 CPU 100% 与该阶段吻合，长尾更可能是 CPU 调度延迟导致。

### 2.2 广播路径

500/1000 人广播时，服务端 Hub 派发平均耗时只有：

- 500 人：`0.453ms`
- 1000 人：`1.115ms`

这说明“Hub 本地派发”本身不是瓶颈，分片后单房间扇出由任务池异步完成，派发路径健康。

## 3. 延迟归因

本轮 `ws_ping` P50 约 39ms，代表测试机到云服务器的基础网络 RTT。

| 场景       | 基础 RTT | E2E P50 | 后端/排队增量 |
| -------- | ------ | ------- | ------- |
| 500 人广播  | 约 39ms | 47ms    | 约 8ms   |
| 1000 人广播 | 约 39ms | 53ms    | 约 14ms  |

因此广播 P95 的 71–99ms，主要构成为：

- 基础网络 RTT 约 39ms
- Kafka 消费平均 7.3–7.7ms
- Hub 派发 0.45–1.12ms
- WebSocket 写队列、k6 接收线程和客户端调度余量

DB、Redis、Kafka 均未成为本轮广播瓶颈：

- DB in_use 峰值：1000 VU 建连时仅 4。
- Kafka lag：全程 0。
- Redis 平均延迟：0.172–0.307ms。
- Hub 等待队列：全程 0。

## 4. 广播扇出率说明

本轮 500 人广播：`448133 / 1275 ≈ 351.5`。

本轮 1000 人广播：`1068884 / 1687 ≈ 633.6`。

扇出率没有达到 500 或 1000，不是消息丢失，而是测试脚本在爬坡阶段就让发送者开始发消息，此时房间成员尚未全部上线。

如果要评估稳态扇出完整性，应改成：

- 先让 500/1000 人全部建连完成；
- 再统一起跑发送；
- 统计稳态阶段每条消息实际触达人数。

## 5. 1000 并发建连的 CPU 瓶颈

### 5.1 时间窗口

本轮 1000 VU 纯建连测试的本地时间窗口为：

- 开始：23:46:29
- 结束：23:47:59
- 服务端活跃连接从 0 平滑增长到 938

如果云服务器监控时间比压测机慢约 20 分钟，则监控上的 23:26 与这个测试窗口基本对应。

### 5.2 为什么 CPU 100% 会解释长尾

- 1000 个 WebSocket 连接会同时产生 1000 个 `ReadPump` 和 1000 个 `WritePump` goroutine。
- 建连过程中每个连接还会执行 Redis 上线写入、数据库房间加载、Hub 注册和指标更新。
- 测试结束时 k6 中断了约 956 个连接，服务端会在短时间内集中处理大量关闭事件、`Unregister`、房间移除和日志输出。
- CPU 被打满时，握手、读循环、写循环和关闭清理都会出现调度延迟，表现为 P95/P99 突然上升到秒级甚至 21s。

### 5.3 当前无法确定是爬坡段还是关闭段

目前服务端没有暴露 `process_cpu_seconds_total`，所以只能确认 CPU 到过 100%，不能确认它发生在：

- 建连爬坡阶段；
- 1000 连接保持阶段；
- 测试结束时的集中断开阶段。

下一步需要按阶段采样 CPU。

## 6. 500 VU 短连接重连风暴

单独复测 500 VU、5 秒短连接并同步重连时，成功率降至 87.89%，P95 建连达到 21s。

这属于“大量客户端同一时刻重连”的拥塞场景，不应作为正常建连容量结论，但它说明：

- 生产客户端断线重连需要加随机抖动和指数退避；
- 网关层需要限制每秒新建连接数；
- 需要为 `connection_duration`、`connections_total` 和 `ws_read_errors_total` 增加告警。

## 7. 下一步建议

1. 在 `/metrics` 中补充 Go 进程指标，至少包括：
   - `process_cpu_seconds_total`
   - `process_open_fds`
   - `process_max_fds`
   - `go_goroutines`
   - `go_memstats_alloc_bytes`
2. 重跑 1000 VU 建连，并分三段采样：
   - 爬坡段 CPU；
   - 满员保持段 CPU；
   - 测试结束关闭段 CPU。
3. 把建连脚本改成“连接完成后延迟关闭”，避免测试结束时 1000 连接同时被中断，区分 CPU 峰值来源。
4. 若确认是关闭风暴导致 CPU 100%，优先优化 `Unregister`/`Stats()` 的锁粒度、日志采样和批量离线写入。
5. 若确认是爬坡段 CPU 100%，优先减少每次建连的同步工作：Redis 上线写入改批量、房间加载加缓存、注册日志降级。
6. 500/1000 人广播继续做 256/512/1024 任务池 A/B，验证任务池容量是否成为下一个限制。
