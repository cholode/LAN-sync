# WebSocket 连接容量阶梯压测报告（perf6）

## 1. 测试概述

- 测试时间：2026-08-18 23:48 ~ 23:52
- 目标地址：`ws://8.130.151.211/api/v1/ws`（经 Nginx 80 端口 → 后端 Go 8080）
- 监控端点：`http://8.130.151.211:6060/metrics`
- 压测工具：k6 v1.6.1 + Node.js 指标采集器
- 数据目录：`perf6/`
- 测试模式：**只建连、不发消息**，连接建立后保持（仅 ping 心跳），直到场景结束统一断开
- 用户准备：先注册+登录拿 JWT（24h 有效），全部拿到后再用 token 压测；实际准备 8400 个用户
- 阶梯：100 → 500 → 1000 → 2000 → 5000（每级独立 k6 运行，失败率 > 5% 即停止，不再跑更高一级）
- 爬坡/保持：100VU(20s/20s)、500VU(30s/30s)、1000VU(30s/30s)、2000VU(60s/30s)、5000VU(120s/30s)

## 2. 总体结论

- 100 和 500 并发建连**成功率 100%**，建连 P50 稳定在 ~82ms。
- **1000 并发失败率 13.87%（149/1074），超过 5% 阈值，停止**。服务端峰值在线 **925**。
- 连接容量天花板在 **500 ~ 1000 之间**，实测接近 925~940（与上一轮 perf4 的峰值在线 938/912 高度一致）。
- **瓶颈不在 Go 应用本身**：压测期间后端进程 CPU 仅 1~2%、goroutine 峰值 ~1971、fd 上限 65535（实际占用 ~2000）、Kafka lag 0、DB in_use 峰值 2。
- 失败连接全部卡在 **~21 秒**（TCP SYN 重传超时特征），而不是被立即拒绝 —— 指向接入层（Nginx）的连接接纳能力。

## 6. 与上一轮（perf4）对比

| 场景 | perf4 峰值在线 | perf6 峰值在线 |
| --- | --- | --- |
| 1000 并发建连 | 938 / 1000（93.8%） | 925 / 1074（86.1%） |

两轮独立测试（不同脚本、不同时间）都卡在 **925~940** 附近，说明这是接入链路上一个稳定的、确定性的容量边界，而非测试误差。

## 7. 根因分析

1. **Go 应用不是瓶颈**：CPU 1~2%、fd 上限 65535、任务池空闲、Kafka/DB/Redis 全部健康。
2. **接入层有 Nginx**（`Server: nginx/1.31.3`）：客户端 → Nginx:80 → Go:8080。每个 WebSocket 经 Nginx 需占用 2 个 fd（客户端→Nginx、Nginx→后端）。
3. 失败呈现 **21s SYN 重传超时**，是「监听队列/连接接纳」溢出的典型信号，与 Nginx 层的 fd 软限制或 `net.core.somaxconn` 监听 backlog 溢出最吻合。
4. 仓库 `deploy/nginx/nginx.conf` 写了 `worker_connections 65535` 但**未写 `worker_rlimit_nofile`**；docker-compose 虽有 `ulimits.nofile: 65535`，但**实际部署是否按此生效需在服务器上确认**。若部署未带该 ulimit（或 host 默认 1024），Nginx worker 会在 ~1024 个 fd 处截断，正好落在 925~1000 连接的观测值上。
5. 直连 8080 的对照测试本次因客户端网络中断作废，未能区分「Nginx 层」与「后端监听 backlog」—— 但后端进程自身的 CPU/fd/goroutine 证据已足够排除 Go 应用本身。

## 8. 建议（按优先级）

1. **在服务器上确认 Nginx 层限制**（一次 SSH 即可定位）：
   - `cat /proc/<nginx-master-pid>/limits | grep open`（看 worker 的 nofile 软限制是不是 1024）
   - `sysctl net.core.somaxconn`（监听 backlog 上限）
   - `nginx -T | grep -E "worker_connections|worker_rlimit_nofile|worker_processes"`（确认生效配置）
2. 若为 fd 软限制：Nginx 主配置加 `worker_rlimit_nofile 65535;`，并确认容器 `ulimits.nofile` 与 host `/etc/security/limits.conf` 生效。
3. 若为 somaxconn：`sysctl -w net.core.somaxconn=4096` 并持久化。
4. 网络稳定后，重跑一次「直连 8080 vs 经 80」的 A/B 对照，彻底隔离 Nginx 与 Go。
5. 继续提升容量前的 Go 侧优化（perf4 已列）：建连日志降级、Redis 上线写入批量化、房间加载加缓存、`Unregister` 的 metrics 全量扫描改原子计数。
